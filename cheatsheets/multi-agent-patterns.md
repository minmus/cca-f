## The reference system

```mermaid
flowchart TB
    CO["Coordinator (hub)<br/>routes · evaluates · re-delegates"]
    CO <--> WS["Web Search<br/>4–5 scoped tools"]
    CO <--> DA["Doc Analysis<br/>4–5 scoped tools"]
    CO <--> SY["Synthesis<br/>4–5 scoped tools"]
    CO <--> RG["Report Generator<br/>4–5 scoped tools"]
    CO -.->|"state manifest"| ST[("Structured state<br/>known location")]
```

## The 3 master rules

| # | Rule | Why |
|---|---|---|
| 1 | **Structure beats instructions** for anything that must be reliable: schemas, scoped tools, gates in code | Prompts are **probabilistic** (~90–95%). Code is **deterministic** (100%) |
| 2 | **Everything goes through the coordinator**, which passes context **explicitly** in the next prompt | Subagents have **isolated context**: *"receives only what the coordinator writes"* |
| 3 | **Be strict about outputs and boundaries, flexible about method** | Reliability where it matters, adaptability where it helps |

## One line per question

| Q | Situation | ✅ Answer | Key idea |
|---|---|---|---|
| **Q01** | Citations lost after summarization | Structured output: content **separate from** source metadata | Free-text summaries drop metadata. Use fields instead |
| **Q02** | What to pass to the report generator | Synthesis draft + **structured source index** (claim → URL + excerpt) | Complete ≠ everything. Pass findings + metadata + links, not 120K raw tokens |
| **Q03** | Pipeline crashed at 12/28 | Agents export structured state → **coordinator loads manifest** → injects into prompts | Exact state, held centrally, handed out selectively |
| **Q04** | Agents call other roles' tools | **18 tools → 4–5 per role** | Fewer, scoped tools = reliable selection. Remove access, don't forbid it |
| **Q05** | Subagent gives up, misses new angles | **Goals + quality criteria**, not steps | Delegate the *what* and *how good*, not the *how* |
| **Q06** | Synthesis flags gaps, coordinator ignores them | Coordinator **evaluates → re-delegates targeted → re-synthesizes** | Closed loop with a cap. After the cap: report gaps / escalate |
| **Q07** | How search → doc analysis info flows | Coordinator **includes findings in the next prompt** | Hub-and-spoke. If it's not in the prompt, the subagent doesn't know it |
| **Q08** | Conflicting estimates: false certainty or vague hedging | Report sections for **established vs contested**, preserving each source's value + method | Annotate conflicts. Don't pick, average or filter |
| **Q09** | Subagents cite correctly, **synthesis** loses links when combining | Structured claim-source mappings that synthesis must **preserve and merge** | Don't reconstruct provenance. Preserve it |
| **Q10** | Synthesis says "no findings were provided" | Coordinator **didn't include** prior outputs in the prompt | API is stateless, subagents isolated. Context exists only if written into the prompt |
| **Q11** | Analysis spots gaps, strict pipeline can't act | Analysis **reports gaps explicitly** → coordinator: targeted search → **re-analysis** → until sufficient | Explicit signal + complete loop (beats inferred signal + half loop) |
| **Q12** | How to give synthesis what it needs | **Complete findings** from both subagents **directly in its prompt** | No inheritance, no callbacks, no shared-store lookups |
| **Q36** | Coordinator says "I'll ask the web search agent…", but no subagent **ever** runs; no errors | **`"Task"` missing from the coordinator's `allowedTools`** | Saying ≠ doing. No tool → no `tool_use` → nothing runs, nothing fails. Exam name "Task" (current Claude Code: "Agent") |
| **Q39** | Follow-up "summarize what we learned" takes 40+ s: coordinator spawns synthesis with 80K+ findings it **already has** | **Coordinator answers simple summaries directly**; spawn only for complex work | Remove the unnecessary hop. *"Selects only the subagents it needs"* (1.2), which may be none |

| **Q17** | One unified order tool → missing / irrelevant params | **Split** into `issue_refund`, `cancel_order`, `request_reshipment`, each with only its required params | Purpose-specific tools (2.1). Make the wrong call impossible to express |
| **Q18** | "Ready to post. Confirm?": 98% approved in 2 s, errors slip through | **Show the details**: full text, account, time, platform | Reviewers can't catch what they can't see. Fix content, not friction |

| **Q21** | Agent over- AND under-escalates on confidence scores | Tool returns scores + **`request_review` flag from tested thresholds** + **`review_reasons`** | Don't let the model interpret raw numbers. Decision in code, per field, with reasons |
| **Q22** | Agent retries after 0 results (HTTP 200, `[]`) | **`success: true` + `results: []`**; `isError` only for real execution failures | Empty ≠ error. "Found nothing" vs "could not search" must be distinguishable |
| **Q23** | "Remove old backups" → `delete_file`; descriptions are one-liners | **Expand descriptions**: when to use / NOT use, which tool instead | Descriptions = primary selection mechanism. "Improve selection" → A; "guarantee" → server-side check |
| **Q24** | Tool raises exceptions → agent says "I'm having trouble" | **Structured error as tool output**: type, retryable, actionable context | The model can only recover from what it can see. Different failures → different next steps |
| **Q25** | MCP: missing required param · API 404 · API 503 | Missing param = **JSON-RPC protocol error**; 404 + 503 = **tool result `isError: true`** | Did the tool run? No → protocol error. Yes but failed → `isError` (model sees it) |
| **Q26** | `send_notification` times out, agent retries → duplicates | Error says **"status unknown, may have been sent, avoid retry"** | Side-effecting + not idempotent → transient ≠ retry-safe. Correct meaning beats structure with wrong meaning |
| **Q27** | Device timeout → agent only says "not responding" | Error with **likely cause + troubleshooting steps** to offer the user | Write errors for the model/user, not a debugger. In-result, not via another tool |
| **Q28** | $500 reimbursement threshold must be tamper-proof | **Tool enforces it internally**: <$500 pay, >$500 create approval request + "pending" | Rule lives in the code that moves money, on real data. No agent-set flags |
| **Q29** | 18+ sequential calls; selection needs editorial judgment over all candidates | **`discover_and_analyze`** composite returning all candidates + scores; `add_to_collection` separate | Combine the mechanical steps; keep the judgment and the action with the model |
| **Q30** | Generic `analyze_document(doc, instruction)` returns wrong output types; 35% re-requests | **Split**: `extract_data_points`, `summarize_content`, `verify_claim_against_source`, each with I/O contracts | The guide's own 2.1 example. Tool choice = task; contract = output shape |
| **Q31** | Refunds > $500 must **automatically** escalate; a clear prompt still fails 3% | **PreToolUse hook**: intercept `process_refund`, block > $500, **invoke escalation** | 100% requirement → hook (1.5, the guide's own example). Enforce the whole rule: block **and** route |

- Loop control: `stop_reason == "tool_use"` → run tool, append `tool_result`, call again · `"end_turn"` → stop. *"The only reliable signal."*

| Need | Use |
|---|---|
| Must **always** happen (money, compliance) | **Prerequisite gate** in the tool / **hook** / fixed **workflow** in code |
| Which hook? (Q31, Q42, Q52) | **Block** before an action (refund > $500) → **PreToolUse**. **Fix/transform** after (format the edited file, trim a result) → **PostToolUse**. Mechanical rule → **command** hook (deterministic); judgment → prompt hook. **Keep the agent out** of something (e.g. `/migrations`) → Claude Code **permission deny rule** `Edit(/migrations/**)` (enforced by Claude Code, deny beats allow and hooks; use `Edit(...)`, not `Write(...)`); sandbox for OS-level (scripts) (Q52 check) |
| Confidence threshold for review? Automate high-confidence items? (Q21, Q95, 5.5) | **Per field**, **tested** on a validation set (known answers), **stricter where mistakes are costly** (amount > vendor). Never one made-up number for all. **Before cutting review on high-confidence items:** break accuracy down **by document type × field** (months of 100% review = a labelled set already). An aggregate (97%) is weighted by volume, so the big easy segment hides weak ones (receipts 72%, international 65%). Automate only the segments that hold up, keep review on the rest. ✗ 97% vs downstream requirements (still the aggregate) ✗ the best single cutoff on the aggregate ✗ pilot straight to production (Q95). **After automating:** review doesn't stop, it becomes **stratified random sampling** of the **automated** items: a sample from **every stratum** (document type, confidence band, field), **high-confidence included**, compared with its validated rate at regular intervals. It catches **novel error patterns** (a big supplier's new layout read wrong at 95% confidence) that your own checks pass (line items do sum to the subtotal). Without it you hear from **downstream failures**. A segment drops → back to human review, re-validate. ✗ sample only low-confidence items (Q95 check) |
| Limited reviewer capacity: who checks what? (Q114, 5.5) | **Field-level** confidence (the error sits in one field) → **calibrate** on a labelled validation set (raw 0.95 can mean 88% or 99% by field) → order the queue by calibrated uncertainty → reviewers take it **from the top**, next item = highest uncertainty left, not the oldest. Add semantic validators for errors you can describe in code (a time unit in `quantity`). ✗ empty fields only (the errors are filled) ✗ "unusual layouts" (a guess) ✗ random 20% (even spread) ✗ raw scores (Q114) |
| Reviewer corrections show a recurring mistake? Inconsistent field format? Empty fields? (Q98, Q112, Q113, 4.2) | **Diagnose the pattern** (which input, which wrong output) → if it's **how the model reads ambiguous text** (an informal amount: convert, omit or copy?) or **empty fields for information that's there** → **2–4 few-shot examples with reasoning** covering exactly that case ("a handful" → `"a handful"`, plus a precise contrast). The reasoning carries over to "a pinch", "a knob". Re-run the corrected cases as a test set. Make sure the field's type can hold the answer (text, not only numbers). ✗ enum label ✗ regex fill-in ✗ fine-tune. **Same field in varying formats, or skipped although it's in the text, despite a schema** ("cotton blend" / "Cotton/Polyester mix" / missing) → decide the **standard**, then **2–4 examples with reasoning** that show it. The schema checks **shape, not wording** (*"the schema guarantees structure, not correctness"*). ✗ bigger model ✗ required field ✗ temperature 0 (Q112). **Which examples?** One per **failure type**: vague ("cotton blend" → names, no shares), other notation ("Cotton/Polyester mix (65/35)" → standard list), **skipped** (material only in running text → extracted). Separators and abbreviations go in the **reasoning** line, not in separate examples. Room for a 4th → no material at all → `null`. Frequency: count it **among the failures** (*"Cover the failing cases"*) (Q112 check). **Strict schema, valid JSON, but `[]` / `null` where the document has the information** in another structure (inline citations vs a bibliography, methods inside the introduction) → **examples of those structures**, with reasoning on how to recognise the content anywhere. Schema = shape only. ✗ regex fill-in ✗ plain re-send ✗ optional + manual review (the info isn't absent) (Q113). **Retry for what's left** → send **the original document + the failed extraction + the specific error** ("`citations` is empty, but the document has markers like [3] and a Sources list"); a regex is a fine **detector** for that error, not a filler. **No retry helps** when the information is genuinely absent, only in an external document not provided, or needs knowledge the model lacks → `null` (if allowed) or human review (4.4) (Q113 check). Few-shot **is** right for reading/judgement; it's **wrong** for rules that must always hold (thresholds, policy, tool design → code: Q17, Q21, Q23, Q34). **The amount isn't in the source at all** ("Garnish with parsley." → model writes "1 tbsp") → **schema first: make the field nullable / optional** (`"type": ["string", "null"]`, required = only what's always there). *"A required field pressures the model to produce a value even when the source has none."* (4.3). ✗ "tell it not to invent" alone (the guide's scenario: *"has not stopped it"*; the schema still demands a value) ✗ another few-shot first (*"Fabrication of missing data should not improve"*). Then an example/instruction for when to use `null` (Q98 check) |
| Batch or real-time? (Q111, 4.5) | Ask **does anyone wait for the result?** Yes (an alert within 30 min, a pre-merge check, a client on the phone) → **real-time API**. No (archive, overnight report, weekly audit) → **Batch API**, 50% off. Mixed traffic → a **router**: same prompt and schema, two transports. A batch has **no latency guarantee** (up to 24 h): never put a deadline on it because it *usually* finishes fast. ✗ all batch ✗ hourly batches + "expedite on return" ✗ all real-time (Q111). **Batch with a promise** ("archived within 36 h") → worst case = a document that just missed a submission: **interval + 24 h ≤ promise** → 36 − 24 = **12 h is the zero-margin limit**; submit more often (every 8 h → 32 h worst case, 4 h spare for collecting, validating, archiving, delays). Guide's version: 30 h → 6 h buffer → every 4 h. An `expired` request has used its 24 h already → resend it real-time to keep the promise (Q111 check) |
| Batch requests failed? (Q110, 4.5) | **Find them by `custom_id`** in the results file → **resubmit only the failures** (*"you pay again for documents that already succeeded"* otherwise) → **with a change that fixes the cause**. Input too long for the context → **chunk** (`doc-123-retry-1-part-n`), then combine per document and validate against the schema. ✗ rerun everything (with caching or a bigger model) ✗ raise `max_tokens` alone (output cap; the input is the problem). (Q67, 5.3) | **1.** Transient → **retry locally, bounded** (e.g. 3 tries, backoff); read-only, so safe (contrast Q26). **2.** Still failing → **structured error context**: **failure type** (transient / validation / business / permission) · **attempted query** · **partial results** · **alternatives** (narrower or split query, other source). **3.** The **coordinator** decides: retry modified, alternative, proceed with partial results, escalate. **Access failure** (never ran → consider retry) ≠ **valid empty result** (ran, found nothing → that's the answer) (Q22 mirror). **4.** Recovery fails, report must ship → include the partial results + a **coverage annotation**: well supported / **limited + why** (*"limited because … was unavailable"*).
